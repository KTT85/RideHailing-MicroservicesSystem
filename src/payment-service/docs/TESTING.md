and deletes all rows in the four business tables before each test. Never point it
at payment_db. On MySQL it runs actual Flyway migrations, including baseline0 for
existing tables. The normal development database is never a test target.

## Local Postman harness

RabbitMQ portable: từ root chạy `./scripts/rabbitmq/start.ps1`. Chạy kiểm thử
listener với broker thật bằng `./scripts/rabbitmq/test-payment.ps1`: dùng vhost
payment-test riêng, H2 cho database, không đụng payment_db. Chi tiết thao tác và
cổng ở `deploy/rabbitmq/README.md` tại root.

Start User, Payment, MySQL and RabbitMQ with its Management plugin. Import
`tests/Payment.local.postman_collection.json`. Set local collection variables:
loginIdentifier/loginPassword, rabbitUser/rabbitPassword. Secrets/tokens must not
be exported or committed. The login response stores passengerId/accessToken.

Run requests in order, manually polling reads until asynchronous processing
finishes. Create/bind the demo queue before PAY so result messages have a route.
Expect PAY SUCCESS, duplicate unchanged, refund REFUNDED, cash completion PENDING,
then cash confirmation SUCCESS. SQL `scripts/check-invariants.sql` verifies money
effects. Repeating a command uses its original eventId. For another demo clear
tripId/cashTripId/correlationId and the four generated eventId variables.

The queue `payment.demo.results` is an observation queue, not a replacement for
Trip/Notification consumers. The harness publishes trusted commands directly to
RabbitMQ only to test Payment independently; it does not test trip authorization.

## Live fault demonstrations (required before claiming system completion)

1. Stop Payment, publish a PAY command. Check it remains in payment.commands.
   Restart Payment with the same database/broker; check SUCCESS, one PAY row and
   one successful charge. Redeliver the command; totals must remain unchanged.
2. Start with PAYMENT_SIMULATOR_TRANSIENT_ATTEMPTS=1 and a long retry delay (e.g.
   PAYMENT_RETRY_SECONDS=30). Publish PAY; observe attempt_count=1 and persisted
   next_retry_at. Stop Payment before due time, restart with the same settings;
   observe SUCCESS without creating another operation.
3. To demonstrate outbox recovery, temporarily remove only the demo result queue's
   binding in the isolated Payment test environment (no Trip/Notification queues),
   then publish PAY. Outbox stays PENDING after mandatory return. Stop Payment,
   restore the binding, restart; the same eventId is published. Do not delete
   production/shared bindings. If already MANUAL_REVIEW, use the admin retry API.
4. Publish malformed JSON through Management; inspect payment.dlq. Reprocessing
   invalid messages requires correcting the cause first and replaying the saved
   message with a stable business key. Database transient failures additionally
   exercise payment.retry; confirm its counter and eventual DLQ after the bound.
5. With Trip implemented, execute group's F02: paid TRANSFER, cancel, stop Trip
   after release and before refund completion, restart, verify REFUNDED exactly
   once and Trip CANCELLED only after refund/release confirmations. Payment alone
   cannot demonstrate the complete Saga.

Capture pre-failure, during-failure and final DB/queue/API/log evidence tied to the
Git revision. Never repair rows manually to simulate successful recovery.

credentials in the current terminal, then:

```powershell

```
